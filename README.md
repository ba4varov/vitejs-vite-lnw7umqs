# Метео Пулс

Уеб приложение за прогноза за времето с търсене на населени места по света, почасова и 14-дневна прогноза, качество на въздуха и чат на български и английски. Публичен адрес: https://ba4varov-wheater.vercel.app/

## Разработка

```sh
npm ci
npm run dev
```

Проверки преди публикуване:

```sh
npm test
npm run lint
npm run build
```

Сайтът използва Open-Meteo за прогноза, местоположения, морски данни и качество на въздуха. Чатът извлича измерванията от прогнозата; Gemini може да помогне за разбирането на свободно формулирани въпроси, когато `GEMINI_API_KEY` е зададен като **сървърна** променлива във Vercel. Ключът не е нужен за основната прогноза и не бива да се добавя в клиентския код или в Git.

При местна разработка `vite` обслужва интерфейса, а Vercel API маршрутите в `api/` изискват Vercel runtime (например `vercel dev`) за пълен тест на чата. Проверявайте прогнозата за градове в различни часови зони и въпросите за днес, утре сутрин и утре вечер след всяка промяна в обработката на времето.

## Реална регистрация и профили (Supabase)

Приложението използва Supabase Auth, а не собствено съхранение на пароли. Клиентът пази само стандартната Supabase сесия и я обновява при презареждане. Профилът и правата се четат през защитения сървърен маршрут `/api/profile`; планът е отделен от профила и не може да се променя от клиента.

1. Създайте Supabase проект с **Enable Data API** включено, **Automatically expose new tables** изключено и RLS включено. Изпълнете целия SQL файл `supabase/migrations/20260930000000_auth_profiles.sql` в SQL Editor (или чрез Supabase CLI). Миграцията изрично отнема подразбиращите се права и дава само минималните `service_role` права, използвани от `/api/profile`, плюс `EXECUTE` на entitlement RPC само за `authenticated`.
2. В **Authentication → URL Configuration** задайте Site URL `https://ba4varov-wheater.vercel.app/` и добавете Redirect URLs `http://localhost:5173/**` и `https://ba4varov-wheater.vercel.app/**`.
3. В **Authentication → Providers → Email** включете Email provider и **Confirm email**. Настройте собствен SMTP доставчик за надеждни реални писма; без SMTP вградената услуга е ограничена и е предназначена главно за тестове.
4. Копирайте `.env.example` като `.env.local`. За локален пълен поток стартирайте `vercel dev`; добавете същите променливи във Vercel Project Settings. `SUPABASE_SERVICE_ROLE_KEY` е само сървърна променлива и никога не трябва да има префикс `VITE_`.
5. В Supabase email templates оставете `{{ .ConfirmationURL }}` за потвърждение и възстановяване: redirect адресът се подава от приложението според текущия origin.

### „Моите места“

След началната миграция приложете **отделно и в този ред** `supabase/migrations/20260930010000_favorite_places.sql` чрез Supabase SQL Editor или `supabase db push`, след което публикувайте frontend-а. Миграцията добавя само таблиците за места и настройки, RLS политики и атомарната функция за място по подразбиране; не променя `profiles`, `subscriptions` или auth trigger-ите. Не са нужни нови environment variables: браузърът използва съществуващите `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`, потребителския JWT и RLS (никога service-role ключ).

Преди production проверете с два реални акаунта: добавяне/изтриване и дедупликация по координати; задаване и изтриване на default; reload и вход от друг браузър; изрично guest→profile прехвърляне; незабавно изчистване при logout/account switch. В SQL Editor с JWT на потребител A потвърдете, че `select`, `delete` и `insert` с `user_id` на B се отказват, както и `select public.set_my_default_place('<place-of-B>')`. Автоматичните Node тестове използват mock storage и не заместват тази реална RLS проверка.

Нов акаунт получава сървърно `free` абонаментно състояние. В момента дори `service_role` няма table grant за промяна на `subscriptions`, защото реалният код не извършва такава операция. Бъдеща интеграция за плащания трябва да добави отделна миграция с минималното необходимо право и да актуализира `subscriptions` единствено от доверен webhook. Интерфейсът няма права за insert/update/delete върху тази таблица. Текущите прогнози, търсене, графики и чат остават публични.

## Cloudflare Turnstile за Supabase Auth

Turnstile защитава регистрацията, входа с парола, възстановяването на парола и повторното изпращане на потвърждение. Токенът от браузъра се изпраща **директно и само веднъж** до Supabase Auth в `gotrue_meta_security.captcha_token`. Няма междинна Vercel проверка. Secret key принадлежи единствено в CAPTCHA настройките на Supabase — никога не го добавяйте във frontend кода, GitHub, `.env` файл или променлива с префикс `VITE_`.

За безопасно въвеждане следвайте точно този ред:

1. В Cloudflare Turnstile създайте widget за реалния домейн (и нужните локални/preview домейни за тест). Запазете отделно публичния **site key** и тайния **secret key**.
2. Във Vercel Project Settings добавете само публичния site key като `VITE_TURNSTILE_SITE_KEY`. За локална разработка може да го добавите в `.env.local`. Не добавяйте secret key във Vercel frontend променливи.
3. Разположете новия код и проверете, че widget-ът се зарежда на четирите защитени действия. Vite вгражда `VITE_` стойностите по време на build, затова след добавяне/промяна на ключа е нужен нов deployment.
4. Едва след това в Supabase Dashboard отворете **Authentication → Settings → Bot and Abuse Protection → CAPTCHA**, изберете Cloudflare Turnstile, въведете **secret key** и включете CAPTCHA.
5. Направете реални проверки на регистрация, вход (включително грешна парола), „Забравена парола“ и повторно потвърждение. Накрая потвърдете с директна заявка към съответния Supabase Auth endpoint, че заявка без валиден CAPTCHA токен се отказва.

Докато `VITE_TURNSTILE_SITE_KEY` липсва **и CAPTCHA още не е включена в Supabase**, формите запазват старото си поведение. Защитата става активна само когато публичният site key е конфигуриран в разположения frontend и CAPTCHA е включена със secret key в Supabase. Не включвайте Supabase CAPTCHA преди frontend deployment: при конфигуриран site key интерфейсът умишлено не изпраща защитена заявка без актуален токен и не заобикаля грешка в Turnstile.

Обновяването на сесията, изходът, промяната на парола от удостоверен recovery поток и редактирането на профила не използват CAPTCHA. Автоматизираните тестове в това хранилище проверяват payload-а и клиентския жизнен цикъл с mock обекти; те **не** са реална проверка на включена CAPTCHA в Supabase. Стъпка 5 остава задължителна след ръчното публикуване и включване.

## Резервно копиране на Supabase

Ръчен криптиран архив и възстановяване само в изолирана среда: [подробно ръководство](docs/supabase-backup-bg.md). Инструментът не се стартира автоматично и не изисква платен Supabase план.

## Google OAuth вход

Google PKCE входът през съществуващия Supabase Auth е изключен по подразбиране (`VITE_GOOGLE_AUTH_ENABLED=false`). [Точна конфигурация, redirect адреси и проверки](docs/google-oauth-bg.md). Не са нужни SQL/RLS промени.
