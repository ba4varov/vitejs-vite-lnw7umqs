# Push диагностика без реално изпращане

## Какво означава отчетеният 502

В проверения main (90f2542) `PUSH_TEST_NOT_CONFIRMED` с HTTP 502 се връща само след получен валиден финален HTTP отговор извън 2xx и успешно `finish_push_test`. Възможни са всички 300–599: пренасочване, невалидна заявка/удостоверяване, липсващ абонамент, ограничение на заявките и грешка при доставчика. 404/410 маркират expired и премахват съответната стара регистрация; 429 прилага Retry-After към глобалния cooldown, а необработимо дълъг срок изключва DB gate. Останалите статуси маркират failed. Няма автоматичен retry.

DNS, TLS, timeout, прекъснат/невалиден/прекалено голям отговор, криптографска подготовка и RPC грешки връщат 503 `PUSH_TEST_UNCERTAIN`. Невалидна VAPID конфигурация връща 503 `PUSH_TEST_UNCONFIGURED` преди DB claim. 409 за несъществуващ permit доказва отказа на gate, но не проверява доставчика. 200 означава приемане от доставчика, а не показване на Note 13 Pro.

## Проверка на веригата

`web-push@3.6.7` формира RFC 8292 ES256 JWT с audience=origin на endpoint-а, sub=конфигурирания контакт и ограничен exp, и `Authorization: vapid t=…, k=…`. Валидират се canonical base64url, P-256 двойката и съответствието с публичния ключ при регистрацията. RFC 8291 aes128gcm payload е проверен чрез дешифриране в тестов приемник. HTTP е POST с TTL 60, urgency very-low, Host на доставчика и точна двоична Content-Length. Тези настройки не гарантират незабавно показване на устройство.

SSRF allowlist и проверката на всички DNS адреси остават. TCP се свързва с проверен числов IP; TLS проверява оригиналното име чрез SNI/hostname и сертификат, ALPN http/1.1. Не се следват пренасочвания и не се опитват следващи адреси след несигурен резултат. Deno използва native connect/startTls/handshake. Node вече запазва остатъка от TLS chunk вместо да отказва валидни кратки headers с голям response body. HTTP парсерът обработва до четири междинни 1xx отговора, с общ лимит 4096 bytes, и отказва 101 upgrade.

`api/push` управлява регистрацията/предпочитанията; не е sender. Forecast модулът е бъдещ адаптер. Service worker показва полученото съобщение с фиксиран same-origin адрес. Единственият текущ еднократен sender е push-test.

## Безопасна диагностика

След операторско удостоверяване отговорът съдържа `diagnostic.category`, числов `providerStatus`, когато е получен, и `phase` при грешка. Edge логът `push_test_result` съдържа само тези полета. Няма endpoint, IP, permit/device/user/claim ID, VAPID ключ, JWT, Authorization, auth/p256dh, response body, произволни headers или exception текст. Отказите преди claim не добавят диагностика. Неуспешно логване не влияе на изпращането. Резултатът от доставчика се отчита преди finish RPC, така че грешка при записването не скрива известния HTTP статус.

Категории: accepted; provider_auth_rejected (401/403); subscription_expired (404/410); rate_limited (429); redirect_refused (3xx); request_rejected (400/413); provider_unavailable (5xx); provider_rejected (други). Отказ на удостоверяване не доказва сам по себе си грешен VAPID ключ. Транспортът различава connect_failed, tls_failed, write_failed, response_failed, invalid_response, response_limit, timeout и transport_failed; DNS и DB имат отделни категории. TLS категорията не излага конкретна сертификатна/системна грешка.

## Една проверка сега — само четене

В Supabase Dashboard → Logs → Edge Functions отворете единствено execution-а на вече направения реален тест (по часа му), за функция push-test и съответната публикувана версия. Проверете дали има записан **числов upstream/provider HTTP status**. Споделете само статуса и часа; не копирайте headers, URL, body или secrets. Не извиквайте функцията отново и не активирайте gate. Старият код няма собствено такова логване: ако записът липсва, тази проверка няма да възстанови точния отказ. Тогава той остава неизвестен до бъдещ отделно разрешен тест с новата диагностика; историческият 502 не може да се обясни достоверно със смяна на ключове или TLS предположения.

## По-малко ръчни действия при бъдещи тестове — предложение

1. При всяка промяна PR CI изпълнява тестове с фиксирани публични тестови scalars, симулиран доставчик и локален TLS. Не са нужни телефон, Production secrets, разрешаване на доставка или нови VAPID ключове. Frozen Deno check проверява entrypoint-а без изпълнение.
2. Само ако е необходим реален тест: след отделно одобрени merge и ръчно публикуване, един защитен операторски инструмент може да събере съществуващото device/category одобрение, да създаде краткотраен permit и да извика функцията точно веднъж. Това е предложение за следващ етап, не внедрен инструмент и не разрешение за изпращане сега. Той трябва да проверява целевия проект, текущите gates, съгласието, revisions и cooldown; да показва само безопасния резултат и да изключва DB gate в finally. Remote runtime secret остава отделна изрично контролирана защита, без автоматично включване. Не поставяйте операторски token в браузъра/inputs/logs.
3. При 502 използвайте категорията; при 503 не повтаряйте същия permit и не заобикаляйте cooldown. 404/410 изискват ново изрично регистриране; 429 изчаква пълния срок; 401/403 изискват проверка преди ново разрешение. Не е нужна повторна регистрация или ротация на ключове при всяка промяна на кода.

В тази работа няма реални push заявки, Production настройки, SQL промени, secrets, нови VAPID ключове, включване на gate, merge или deploy.
