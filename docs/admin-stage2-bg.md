# Meteo Puls — административен панел, етап 2

## Промени

Подробностите за потребителя са в компактна адаптивна карта. Търсенето е под заглавието „Потребители“ и остава достъпно при зареждане. Плановете и методите email/Google са преведени на BG/EN. UUID е съкратен, разкрива се с native details/summary и се копира с потвърждение; при отказ на Clipboard API има инструкция за ръчно копиране.

Любимите градове се зареждат при избор на потребител чрез `GET /api/admin?action=favorites&id=<UUID>` и `admin_user_favorites(uuid)`. Има отделни състояния за зареждане, празен резултат и грешка. 401/403 скриват административните данни. Няма редактиране или изтриване.

Системното табло има три еднакви карти: Supabase, административен API и Open-Meteo. Всяка показва достъпност, обхват, време на проверката, продължителност, последен успешен час и проблем. Синьото „Услугата е достъпна“ означава успешна конкретна проверка, а не пълна функционална изправност. Няма общ зелен индикатор.

## Какво измерват проверките

- Supabase: след успешна Auth JWT проверка и проверка на членството, изпълнява допълнителен `is_meteo_admin` RPC. Продължителността на картата измерва този RPC, а не общото време за удостоверяване или целия API HTTP round trip.
- Административен API: успешното изпълнение на защитения `system` handler и валиден `admin_users` RPC само за текущия администратор. Продължителността измерва този SQL RPC. Не проверява всички административни функции и не връща потребителски записи в health отговора.
- Open-Meteo: отделна сървърна заявка за текуща температура за София; проверява HTTP успех и крайна числова температура. Не проверява всички градове, прогнози или публичния weather flow.

При невалиден JWT/липса или отнемане на права няма health данни — API връща 401/403. При първоначална недостъпност на удостоверяването се показва обща грешка, а не измислени резултати. След удостоверяване независима грешка на probe се показва в съответната карта. Timeout: 10 секунди за Auth/RPC, 8 за Open-Meteo. Подробности за upstream грешки и ключове не се връщат.

Проверки се изпълняват само при отваряне на раздела и „Провери отново“. Смяна на език, тема и автоматично обновяване на JWT не пускат проверки. Няма interval, cron или keep-alive. Последните успешни времена се пазят само в паметта на текущия панел; неуспешен probe не ги заменя. При logout, смяна на акаунта или презареждане се изчистват.

## Сигурност и ръчна миграция

Новите API действия използват настоящия Supabase Auth JWT и UUID членство. SQL функцията повтаря проверката с `auth.uid()` и `is_meteo_admin()`, има `security definer`, празен `search_path`, квалифицирани таблици и grant само към authenticated. PUBLIC, anon и service_role нямат execute. ID се валидира като UUID и се подава като JSON RPC параметър. Няма нови секрети или service-role заявки, публични API промени, промени по регистрация, сесии, Google OAuth, публични любими места или прогнози.

Прилагането не е автоматично и не е извършено върху Production:

1. Проверете проекта и направете backup преди Production промяна. Етап 1 трябва вече да е приложен. Не изпълнявайте отново миграцията от етап 1 и не създавайте нов администраторски акаунт.
2. Прегледайте `supabase/migrations/20261008010000_admin_user_favorites.sql` и го приложете първо ръчно в отделен тестов Supabase проект чрез SQL Editor с права на собственик.
3. Проверете RPC с обикновен акаунт (403), без валиден JWT (401), с администратор (само градовете на избрания UUID), с потребител без градове (празен списък) и след отнемане на членство (403).
4. След преглед и собствено решение приложете само новия файл ръчно в правилния Production проект. Кодът не изпълнява миграции. До прилагането картата за любими градове показва ясна грешка, без резервни данни.
5. За rollback собственикът може ръчно да изпълни `drop function public.admin_user_favorites(uuid);`. Това не премахва потребители или любими градове; новият UI ще показва недостъпност на прегледа.
