# Административен панел Meteo Puls

## Реализирано

`/admin` е отделен адаптивен интерфейс с BG/EN, светла/тъмна тема, странично меню, табло, потребители, системно състояние, собствен профил, връщане към сайта и изход. Публичният сайт получава единствено линк „Администрация“, след успешна сървърна проверка.

Таблото използва реални SQL агрегати: всички записи в `auth.users`, регистрации за последните 7/30 дни, записи в `favorite_places`, Free/Pro записи в `subscriptions`. Плановете се броят според записания `plan`, независимо от subscription status. Графиката е за 30 календарни дни по UTC, включително текущия; броячът за 30 дни използва подвижен период от 30 дни. При проблем няма примерни или резервни стойности, а съобщение за недостъпност. Нулата означава действителен SQL count.

Списъкът показва имейл, регистрация, последен вход, доставчици от системните Auth metadata, план и основни подробности. Търсенето е нечувствително към регистъра и буквално (знаците `%` и `_` не са wildcard). Страницата съдържа до 20 потребители с подредба по дата и UUID. Липсващите стойности са обозначени като „Няма информация“.

## Защита

`GET /api/admin?action=access|stats|users|system` валидира JWT чрез Supabase Auth `/auth/v1/user`, след което извиква `is_meteo_admin` със същия JWT. Невалидна/изтекла сесия връща 401; валиден обикновен потребител — 403. Други HTTP методи — 405; невалидни параметри — 400. Отговорите са `private, no-store` и варират по Authorization. Грешките не разкриват Supabase подробности.

SQL функциите за данни имат собствена проверка на членството. Така обикновен потребител не може да заобиколи API чрез директен RPC. Таблицата за права е с RLS, без grants за browser или service_role. Административният API използва само anon ключ + JWT, а не service-role ключ. Съществуващият service-role ключ за `/api/profile` остава сървърен. Няма административни полета в публичните API отговори. Няма операции за промяна, изтриване, блокиране или абонаменти.

## Ръчно активиране

1. Прегледайте PR и SQL файла `supabase/migrations/20261008000000_admin_readonly.sql`. Не добавяйте автоматично изпълнение на миграции в CI/Vercel.
2. Първо използвайте отделен тестов Supabase проект с предходните миграции. Приложете новия SQL ръчно през SQL Editor с права на собственик. Функциите са `security definer` с празен `search_path` и изцяло квалифицирани таблици. Не изпълнявайте файла повторно върху вече мигриран проект.
3. Собственикът трябва да има потвърден съществуващ акаунт с имейл и парола. В Supabase Dashboard → Authentication → Users намерете лично неговия акаунт и копирайте UUID. Проверете внимателно самоличността и проекта. Не поставяйте UUID или имейла в код, Git, PR или публични бележки.
4. Само в SQL Editor на избрания проект заменете placeholder с лично проверения UUID и изпълнете:

```sql
begin;
insert into public.admin_memberships (user_id)
values ('REPLACE_WITH_VERIFIED_USER_UUID'::uuid)
on conflict (user_id) do nothing;
commit;
```

5. Потвърдете членството в Dashboard. Членството не се получава чрез регистрация, `user_metadata`, профил или абонамент. Никоя браузърна роля не може да го създава/променя. Правата са по UUID, така че смяна на имейла не ги прехвърля на друг акаунт.
6. В съществуващите Vercel настройки проверете `SUPABASE_URL` и `SUPABASE_ANON_KEY` (server), `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` (browser) — за един и същ проект. Запазете `SUPABASE_SERVICE_ROLE_KEY` само като сървърна променлива без `VITE_`. Не добавяйте ключове в Git. Няма нови платени услуги. Google OAuth не е необходим и настройките му не се променят.
7. Изпълнете тестовете по-долу в тестова среда. След отделно одобрение от собственика за Production направете backup, приложете миграцията ръчно в правилния проект и предоставете членство на лично проверения Production UUID. Прегледайте и слейте PR ръчно; използвайте установения процес за публикуване. Тази задача не изпълнява тези Production стъпки.
8. Влезте с настоящия имейл/парола. Проверете линка „Администрация“, директно `/admin`, презареждане, изход и достъп с обикновен акаунт. API трябва да връща 401 без валиден JWT и 403 за обикновен акаунт; директните RPC за административни данни също трябва да са забранени.

За отнемане на права собственикът изпълнява само в SQL Editor:

```sql
delete from public.admin_memberships
where user_id = 'REPLACE_WITH_VERIFIED_USER_UUID'::uuid;
```

Следващата заявка ще бъде отказана. Вече видени данни в браузъра не могат да бъдат изтрити дистанционно; при отказ/смяна на сесията панелът скрива заредените данни.

### Реални SQL и HTTP RPC проверки

Използвани са временни Docker контейнери `postgres:17-bookworm` и `postgrest/postgrest:v13.0.7`. PostgreSQL е с `--network none`, а PostgREST споделя неговото изолирано мрежово пространство. Няма публикувани портове, връзка с Production, постоянни данни или платени ресурси. JWT ключът се генерира само за изпълнението, не се записва и не се извежда. Контейнерите се премахват след тестовете.

В тестовата база е създадена минимална съвместима Auth схема: роли `anon`, `authenticated`, `service_role`, таблица `auth.users` и функция `auth.uid()`, която чете claims на PostgREST. Това е изрична тестова замяна на Auth схемата, а не пълна Supabase инсталация. Върху реалния PostgreSQL са приложени без замяна всичките четири миграции от проекта, включително административната.

| Проверка | Действителен резултат |
| --- | --- |
| Директни `admin_statistics()` и `admin_users()` като обикновен потребител | PostgreSQL отказ с `insufficient_privilege`; HTTP RPC 403 |
| INSERT/UPDATE/DELETE в `admin_memberships` от authenticated потребител | Отказ за недостатъчни права |
| Самоприсвояване чрез user metadata `role=admin`, `is_admin=true` | Не дава членство |
| Анонимно извикване/самоприсвояване | SQL отказ; HTTP RPC без JWT 401 |
| Service-role RPC и самоприсвояване | SQL отказ; не са дадени grants |
| Явно упълномощен администратор | Реални агрегати от записи: total=3, last7=1, last30=2, favorites=1, free=2, pro=1; графика с 30 дни |
| Търсене и странициране от администратор | Реални SQL резултати; case-insensitive търсене и празна втора страница |
| Липсващ JWT subject | SQL отказ; валидно подписан JWT без subject получава HTTP 403 |
| Невалиден, подправен или изтекъл администраторски JWT | Реалният PostgREST връща HTTP 401 преди достъп до административните данни |
| Отнето членство при все още валиден JWT | Следващият HTTP RPC връща 403 |
| Различна DB timezone | Датите в графиката остават UTC |

При прегледа е коригиран календарът на графиката в миграцията: генерирането използва UTC timestamp дни, а сравненията преобразуват границите изрично към UTC. Така датите и интервалите не зависят от timezone или DST на PostgreSQL сесията. Нова проверка задава `America/Los_Angeles` и потвърждава първия/последния UTC ден. Миграцията продължава да е само за ръчно приложение.
