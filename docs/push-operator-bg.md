# Еднократен операторски Push тест към Note 13 Pro

Инструмент: `node scripts/push-operator.mjs PROJECT_REF USER_UUID DEVICE_UUID APPROVER_UUID wind`.
Няма автоматичен merge, deployment, SQL rollout, промяна на Secrets, VAPID, registration flags или съгласие. Тази промяна не изпраща реално известие. Използването за реален тест изисква отделно изрично разрешение. Поддържа се само предварително одобрен **изолиран тестов проект**; не настройвайте инструмента срещу Production.

## Еднократна подготовка от DB owner

1. След преглед приложете `20261013050000_push_operator.sql` само в изолирания проект и публикувайте обновената `push-test` чрез съществуващата ръчна процедура. Не стартирайте publish workflow, чиято проверка изисква disabled flag, докато flag е enabled. Версиите на SQL и Edge трябва да се обновят заедно; старата Edge не затваря gate при ранна грешка, старият SQL не поддържа scoped permit.
2. DB owner потвърждава, че проектът е изолиран, и задава `push_controls.operator_environment='isolated-test'` само там. По подразбиране е NULL и подготовката отказва. Съществуващият `registration_test_user_id` трябва да е избраният акаунт. Registration gates остават изключени след доброволната регистрация. Не се сменят VAPID ключовете. Собственикът проверява от собствения Note 13 Pro, че browser permission и съгласието са дадени, и свързва **точния device UUID** с телефона; label/UUID сами по себе си не доказват модел на хардуера.
3. Осигурете `psql` и външна libpq service конфигурация за DB owner, плюс доверен Supabase CA файл. Задайте `PGSERVICE` и `PGSSLROOTCERT` в доверения операторски terminal. DB credentials се управляват извън този инструмент чрез съществуващия одобрен механизъм (`PGPASSFILE`/друг libpq authentication); не се създават или съхраняват от инструмента. Използвайте краткотрайна сесия, ако инфраструктурата я поддържа. Няма нов административен token, service-role key или password file в repository, GitHub Actions или tool configuration. `PGPASSWORD` се отказва. Host е фиксиран към `db.PROJECT_REF.supabase.co`, TLS е `verify-full`; pooler/произволен connection URL не се приема. При липса на директен DB достъп спрете; не изключвайте TLS или проверките.
4. Съществуващият Edge flag трябва вече да е изрично разрешен за отделния тест. Ако `PUSH_TEST_DELIVERY_ENABLED` не е `true`, инструментът спира, без DB permit. Не може безопасно да го включи: това би изисквало допълнителни Supabase административни права и би премахнало независимата конфигурационна защита. Най-краткият сигурен вариант е собственикът да провери/разреши този flag ръчно за изолирания проект след отделно одобрение и да го изключи след теста. Не променяйте Production или Secrets по време на настоящата задача.

## Един бъдещ одобрен тест

1. Стартирайте командата с проверените project/account/device/approver UUID. Одобрителят трябва да е действителен активен член на `admin_memberships`. Категорията трябва вече да е разрешена от потребителя.
2. Въведете **съществуващия** операторски token на скрития prompt. Не го поставяйте в аргументи, shell history, environment, файл или log. Не използвайте service-role key или потребителски JWT. Изключете terminal recording/debug tracing.
3. Инструментът проверява flag/token/VAPID двойката на Edge без доставка, после DB owner подготвя revoked permit за 2 минути: точно избрания акаунт и device, текущите revisions, съгласие, градове, категория, plan, акаунт/одобрител, срок и cooldown. Следва отделна Edge проверка на subscription encoding/curve/endpoint и съвпадението на публичния VAPID ключ. Subscription секретите не напускат Edge в отговора. Няма claim или мрежова заявка към доставчика при preflight.
4. Проверете показаните IDs. Само точната фраза `SEND ONE PROJECT_REF USER_UUID DEVICE_UUID` разрешава **максимум един опит**. Отказ/Ctrl-C преди arm не разрешава доставка. Потвърждението не отменя текущото потребителско съгласие; SQL проверките се повтарят при arm, claim и authorize.
5. Прочетете категорията и числовия `providerStatus`; `null` означава, че не е получен валиден финален HTTP статус. 201/2xx означава приемане, а не доказано показване на телефона. 401/403: проверка на удостоверяването; 404/410: собственикът трябва доброволно да регистрира отново; 429: запазен е provider cooldown. При timeout/503/неизвестен резултат **не повтаряйте**. Нов процес може да подготви нов permit само след отделно ново одобрение; няма автоматичен retry/resume.

## Затваряне при приключване и грешка

DB boolean `test_delivery_enabled` никога не се записва като true при arm/claim. Отваря се само вътре в кратката DB транзакция за проверка и се затваря преди commit; при грешка транзакцията се връща назад. DB owner arm създава отделен scoped gate за точно един permit, валиден максимум 60 секунди. Стар/произволен permit няма достъп. Този scoped gate не може да се arm-не от service_role или клиент.

`authorize_push_test` изгаря разрешението и затваря scoped gate **в същата транзакция преди HTTP POST**. Edge `finally` и CLI `finally` също затварят gate и оттеглят permit при отказ/DNS/crypto/provider/DB грешки. Затварянето на стар permit не затваря нов операторски lease. Няма retry на доставка или cleanup. При SIGKILL, изгубена машина или недостъпна DB не може да се гарантира незабавен физически cleanup: boolean остава false, scoped разрешението изтича и се отказва от DB clock след максимум 60 секунди. Не се твърди, че offline процес може да запише DB. При непотвърден cleanup инструментът спира с грешка; DB owner проверява само boolean/lease/revoked/ledger и затваря останалия lease. Не копирайте subscription редове или secrets.

Без runtime secret automation, повишени browser права, автоматична регистрация, променени предпочитания, ключова ротация или отписване. Разрешението може да се използва само веднъж; ledger/cooldown/DNS pinning/TLS/operator authentication и повторната проверка на текущото съгласие остават независими защити.

## Проверки без реален Push

`node --test --test-isolation=none tests/unit/push-*.test.mjs` проверява preflight, потвърждение/отказ, точно един опит, cleanup, redaction, категории, crypto и локален TLS fixture. `node scripts/test-admin-sql.mjs` прилага действителните миграции в disposable PostgreSQL с `--network none` и проверява grants, избрания акаунт, scoped expiry, затворения boolean, повторна авторизация и оттеглено съгласие. Всички SQL fixtures се връщат назад; не се приема външен DB URL. PR CI изпълнява unit и SQL проверките без project secrets; frozen Deno check остава.

Локално на 13 октомври 2026 г.: всички **284 unit проверки** преминаха; отделно **21 целеви Push/operator проверки** с изрично броене преминаха. PostgreSQL/PostgREST SQL регресиите, новата миграция и operator fixtures преминаха, включително оттеглен environment marker и променена device revision между claim/authorize. `lint` е без предупреждения, `typecheck`, `git diff --check`, actionlint 1.7.12 и frozen Deno 2.5.6 entrypoint check преминаха. Архивите на Deno/actionlint съвпадат със SHA-256 от съществуващия CI. TLS проверката използва доверения системен CA bundle, без insecure флагове. Публикувана Edge версия, Production DB/Secrets, реален доставчик и показване на Note 13 Pro не са проверявани или променяни.
